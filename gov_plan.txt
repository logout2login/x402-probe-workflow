PAYMENT-REQUIRED	Server → Client（402）	Base64 PaymentRequired object

# ownsite-aeo v2.0 完整计划书

## 执行摘要

v1.x 已建成一套可运行的 verified data vending 系统：Ed25519 签名的 `verification.json`、evidence refetch 与 hash 比对、TTL/recall 状态机、x402 支付闸门、D1 持久化、公开 dashboard、Durable Object 原子锁、cursor 签名与分页。系统技术上已经“能跑”。

v2.0 不重做这些。它解决的是三个**结构性缺口**：

1. **协议兼容缺口**：v2.0 代码仍在使用 V1 的 `X-PAYMENT` header，而 x402 V2 已标准化为 `PAYMENT-REQUIRED` / `PAYMENT-SIGNATURE` / `PAYMENT-RESPONSE` 三件套。不迁移，等于对新版 Agent SDK 关闭大门。
2. **信任可组合性缺口**：v1.x 只解决“买之前能不能验”，完全不解决“买之后能不能向下游证明我引用过什么”。这是多 Agent 协作的核心失败点。
3. **信号与定价缺口**：Agent 缺少机读的预算保护、决策可用性标识、以及“其他 Agent 实际接受过”的真实使用信号。

**战略判断**：v2.0 的重心不是再建一层基础设施，而是**把已有的验证能力包装成 Agent 效用函数可以直接消费的确定值输入**。执行顺序遵循“零成本高回报优先”：**V2 header 迁移 → description 改写 → budget/decision_usability → L5 attestation MVP → 根据真实数据决定是否扩张**。

## 二、系统架构：L1–L5 分层

v1.x 的十六个版本不被丢弃，而是重新归位。v2.0 新增的是 **L5**，并补完 L2 / L4 的缺口。

```
┌─────────────────────────────────────────────────────────────────┐
│ L5  Composability Layer（v2.0 新建，最高优先級）                 │
│     AgentAttestationToken / Acceptance Registry                 │
│     Inter-Agent Trust Protocol / 下游离线验证                    │
├─────────────────────────────────────────────────────────────────┤
│ L4  Transaction Layer（v1.4 / v1.12 已有；v2.0 补退款）          │
│     x402 V2 支付 / facilitator fallback / preview / refund      │
├─────────────────────────────────────────────────────────────────┤
│ L3  Verification & Trust Layer（v1.1–v1.3 / v1.5 / v1.8 / v1.15）│
│     Ed25519 / evidence refetch / TTL / recall / held / dashboard │
│     decision_usability（v2.0 新增）                              │
├─────────────────────────────────────────────────────────────────┤
│ L2  Signal Layer（v1.10 / v1.11 已有；v2.0 强化）                │
│     agent-index / machine_tags / budget_hint（v2.0 新增）        │
├─────────────────────────────────────────────────────────────────┤
│ L1  Discovery Layer（v1.0 / v1.10 已有）                         │
│     agent.json / agent-index / jwks.json / MCP                  │
└─────────────────────────────────────────────────────────────────┘
```

### 2.1 L5：可組合信任層（v2.0 核心新建）

**为甚麼這是最高優先級**：支付軌道（x402、Mastercard Agent Pay、Visa agentic checkout）認證的是交易，不是 Agent 主體；“誰授權了這筆花費、誰為它背書”被推遲到一個獨立的身份層。v1.x 的 `verification.json` 解決了數據源的可信度，但買家 Agent 引用數據後，**無法向下游證明自己引用的是什麼**。

**模塊構成**：

| 組件 | 作用 |
|---|---|
| `AgentAttestationToken` | 購買後簽發的 Ed25519 憑證，攜帶 `verification_hash`、`intended_use.context`、`forbidden_contexts` |
| `acceptance_registry`（D1） | 記錄所有憑證與下游驗證次數，產生**真實使用紀錄** |
| `POST /attest` | Agent 憑 `purchase_tx_hash` 換取憑證 |
| `GET /acceptance/{package_id}` | 查詢某包的 attestation 數量與下游驗證次數 |
| `POST /acceptance/verify` | 下游 Agent 離線驗證憑證，成功後自動遞增 `downstream_verifications` |

**護城河升級**：v1.x 的護城河是 “recall 紀錄 + refetch 通過率”。L5 加入 **acceptance registry**——這是“其他 Agent 的實際接受紀錄”，比 q 分數更難偽造，因為它綁定真實鏈上購買。

**關鍵約束**：同一 `purchase_tx_hash` 只能簽發一次憑證（`attestation_log` 的 UNIQUE 約束）。憑證的 `expires_at` 與 `verification.json` 同步；包被 recall 時，已有憑證不會被沒收，但新憑證停止簽發。

### 2.2 L2 強化：machine_tags 與 budget_hint

**machine_tags 擴展**：

```json
[
  "tier:featured", "q:0.81", "q_effective:0.79",
  "evidence:6", "source_diversity:0.67",
  "freshness_days:8", "claim_specificity:0.77",
  "domain:ai-adoption", "license:commercial-use",
  "attestation_count:12", "downstream_verifications:34"
]
```

`attestation_count` 和 `downstream_verifications` 是 v2.0 新增的**实际使用信号**，直接回应 Agent 的“选择信息熵”痛点——它们提供的是“其他 Agent 做了什么”，而不是“评分预测了什么”。

**budget_hint 協議**：

- Agent 在 `PAYMENT-SIGNATURE` 之外可携带 `X-Agent-Max-Spend-USDC`（單位：micro-USDC）
- Server 在 402 之后、verify 之前检查；超额返回 `402 budget_exceeded`
- **顺序关键**：先 402 告知价格，Agent 带 payment + budget 重试，避免无 payment 请求被误判
- 未携带 header 时不拦截——协议是选择性的，不增加 Agent 的强制负担

### 2.3 L3 補充：decision_usability

`verification.json` 新增運行時注入字段（**不在 Ed25519 簽名範圍**）：

```json
"decision_usability": {
  "can_enter_decision_branch": true,
  "can_be_cited": true,
  "can_be_redistributed": false,
  "recommended_max_age_hours": 168,
  "verification_cost": "O(1) — single hash check via JWKS",
  "refetch_cost": "O(1) — single HTTP fetch + hash compare"
}
```

這讓 Agent 在 runtime 快速區分“可以入決策分支”與“只可以參考”，而不需要解析模糊的 `hallucination_boundary`。

### 2.4 L4 補充：退款機制

v2.0 只做**請求記錄與狀態查詢**，不做自動鏈上轉賬：

- `POST /refund/{tx_hash}`：24 小時窗口；條件為 `package_recalled` 或 `q < 0.68`
- `GET /refund/{tx_hash}`：查詢 `pending / completed / failed`
- 每筆交易只能申請一次（`refunds.original_tx_hash UNIQUE`）
- **自動轉賬推遲到 v2.1**，因為 `payments` 表只存 pseudonym，不存原始 payer 地址；加密存儲地址是獨立的安全設計

**MVP 不做**：

- `POST /acceptance/verify`（下游驗證端點）
- 離線驗證 SDK
- 完整協議文檔

**為甚麼先做 MVP**：Attestation 的價值依賴多 Agent 生態成熟度。如果 MVP 上線後 4 週內 `/attest` 調用率接近零，說明需求不成立，停損；如果調用率可觀，再投入 4–6 週做完整版。

| **合計** | **$7–8 / 月** |

### 4.3 ROI 的誠實判斷

v2.0 的直接收入不會因為功能增加而自動增長。$0.50–$1.00 / package 的定價意味着即使月銷 100 個，年收入也只有 $600–$1,200。

**v2.0 的 ROI 來自三件事**：

1. **Phase 0 的描述改寫**：成本 2–3 天，可能改變 Agent 的選擇行為（Bazaar 94.4% 的 listing 缺少 use-when 句子）
2. **`budget_hint`**：協議簡單，但直接回應“談判地獄”和失控花費的痛點
3. **`acceptance_registry`**：只有它能在長期形成**時間累積型護城河**——但前提是 Attestation MVP 證明 Agent 會用

**如果 MVP 失敗**，Phase 3 不執行，總投入控制在 9 週以內。這是計劃書最重要的風險控制設計。

### 4.4 定價假設與 E2 實驗

Bazaar 數據顯示中位價 $0.01，94.8% 的 listing 低於 $0.10。v2.0 維持 $0.50–$1.00 的 verified premium tier 定價，但 **E2 實驗必須加入 $0.05–$0.10 的 micro-pack 測試組**，直接測主流價格帶的 demand。如果 micro-pack 轉化率顯著高於 premium pack，定價策略需要重新評估。

## 五、風險與對策

| 風險 | 對策 |
|---|---|
| **V2 header 遷移破壞現有 Agent** | 雙讀 `x-payment` + `payment-signature`，不強制中斷 V1；CDP facilitator 同時接受兩者 |
| **自買/關聯錢包製造 settle** | **絕對禁止**。Bazaar 30 天規則是“移除”，不是永久封禁；寧可掉出再上，不偽造數據 |
| **Attestation 偽造** | Ed25519 簽名 + JWKS 離線驗證；同一 `purchase_tx_hash` 只能簽發一次 |
| **acceptance registry 被刷** | 憑證綁定真實鏈上購買；無購買無法產生 attestation |
| **Agent 不使用 attestation** | Phase 2 MVP 的停損機制；4 週內 `/attest` 調用接近零即停止擴張 |
| **退款被濫用** | 24h 窗口 + 條件限制（`recalled` / `q < 0.68`）+ `UNIQUE` 約束；v2.0 只記錄不轉賬，審批在系統外 |
| **HKMA 合規聲稱過度** | 只寫“aligned in spirit, not certified”；只放 B2B 金融 packs，不全站放 |
| **Bazaar 精確數字被質疑** | 引用時標注“Tanod 索引”，不冒充 CDP 官方數據 |

## 七、一句話結論

**v2.0 的成功不取決於功能數量，而取決於執行順序：先用 2–3 天完成 V2 header 遷移和 description 改寫（零架構改動、直接影響可發現性與兼容性），再用 2–3 週補完 budget 與 decision_usability，然後用 4–6 週的 Attestation MVP 驗證需求，而不是一次性押注 17 週。三個政策窗口——x402 V2 的協議標準化、Bazaar 的描述質量真空、HKMA 的意圖為本問責方向——都是真實的，但它們只提供“勢”；車仍然要自己開，而開車的第一步是把兼容性 bug 修好。**



除了你已经知道的 **Base Builder Grant（最高 $5,000）** 之外，搜索结果里还有几类更实际、更容易拿到的“助力”。它们不全是现金，有些是直接帮你**省掉最大的运营成本**，有些则是**和你现有产品形态高度匹配的奖金池**。
